# Browser Runtime Constraints and Candidate Routes

**Research date:** 2026-10-03. This is a capability review, not a performance result or an architecture decision. No supported device/browser matrix, park scale, frame-time budget, memory budget, offline requirement, or hosting/embedding constraints have been agreed.

**Sources and versions consulted:** MDN Web API and WebAssembly reference pages (living documentation, accessed 2026-10-03); three.js latest release `r186` and its current API/manual pages; Godot latest stable release `4.7.2-stable` (released 2026-08-18), with web-export claims checked against both versioned `4.7` documentation and the moving `/stable/` documentation URL, which matched at research time; Babylon.js latest release `9.29.0` is noted only as an alternative, while its cited documentation tracks `master` and is not release-pinned. Recheck live browser compatibility data and pin library versions before a prototype. Statements below are separated into documented capability and inference; no throughput or capacity is claimed.

## Browser capabilities and constraints

**Rendering.** WebGL 2 exposes an OpenGL ES 3.0 canvas context and is marked Baseline/Widely available by MDN. WebGPU supports render and compute pipelines but remains marked “Limited availability” and requires a secure context (normally HTTPS). Therefore, a WebGL 2 path is the defensible compatibility floor until target browsers are named. Feature-detect WebGPU at runtime; do not infer support from browser brand alone. three.js `WebGPURenderer` tries WebGPU and can fall back to a WebGL 2 backend, but its manual still calls the renderer experimental and notes that some features are missing or may perform better on `WebGLRenderer`. Its custom shader and post-processing migration caveats also matter if the game later relies on those APIs. **Inference:** keep game rules independent of renderer choice and treat WebGPU as an optional rendering experiment, not a simulation requirement. ([MDN: WebGL 2](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext), [MDN: WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [three.js r186](https://github.com/mrdoob/three.js/releases/tag/r186), [three.js WebGPURenderer](https://threejs.org/manual/pages/webgpurenderer.html))

**Picking and repeated objects.** three.js `Raycaster` supports mouse picking and returns an `instanceId` for an `InstancedMesh` hit. `InstancedMesh` shares geometry/material while varying transforms and optional per-instance color, which is a documented fit for repeated scenery, guests, or repeated track-piece meshes. **Inference:** keep tile/path/coaster topology and placement validation in the simulation/domain model; use renderer hits only to identify a tile or rendered object, since a mesh hit does not define park rules. Babylon.js `9.29.0` is a credible higher-level renderer/engine alternative: its current docs describe hardware instancing and say instances are supported for picking, rendering, collisions, and shadows. Verify current `master` APIs against the pinned package if chosen. ([three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html), [three.js Raycaster](https://threejs.org/docs/pages/Raycaster.html), [Babylon.js 9.29.0 release](https://github.com/BabylonJS/Babylon.js/releases/tag/9.29.0), [Babylon.js instance docs](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/copies/instances.md))

**Workers and threads.** Dedicated Web Workers can move simulation away from the UI thread; ordinary messages use structured-clone/transfer mechanisms. Shared memory via `SharedArrayBuffer` needs a cross-origin-isolated page. MDN documents `Cross-Origin-Opener-Policy: same-origin` together with `Cross-Origin-Embedder-Policy: require-corp` or `credentialless`, and a non-blocking `Permissions-Policy: cross-origin-isolated`. This enables worker sharing but constrains popups and cross-origin resources/iframes: embedded assets must opt in through CORS/CORP as applicable. Thus worker offload is available without shared memory, while threaded JS/Wasm adds deployment coupling. A worker also adds snapshot/command synchronization work; whether it improves frame pacing depends on the workload and should be measured. ([MDN: Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers), [MDN: `crossOriginIsolated`](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/crossOriginIsolated), [web.dev: COOP/COEP](https://web.dev/articles/coop-coep))

**Wasm boundary.** WebAssembly modules can export callable functions and expose linear memory to JavaScript; they do not by themselves provide DOM/browser APIs. A narrow batch API—load/initialize park state, advance fixed ticks, return guest/queue/ride state or deltas—would avoid crossing the JS/Wasm boundary per guest or per field. That boundary shape is an engineering proposal, not a measured performance result. Emscripten documents that browser pthread support depends on shared memory and COOP/COEP headers. Keep Wasm conditional on either a reusable native simulation core or profiling that identifies simulation CPU as a material bottleneck; “near-native” capability does not prove this specific workload will be faster end to end. ([MDN: WebAssembly concepts](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/Concepts), [MDN: WebAssembly.Memory](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Memory), [Emscripten: Pthreads](https://emscripten.org/docs/porting/pthreads.html))

**Saving and delivery.** IndexedDB stores structured data asynchronously and is suitable for local park saves; browser quotas and eviction rules vary. Treat browser saves as best-effort unless `navigator.storage.persist()` is granted, and consider an explicit export/import format if saves must survive site-data clearing or move between devices. Serve game assets over HTTPS; set correct `application/wasm` MIME type and compression for Wasm exports. COOP/COEP should be a deliberate deployment decision tested with actual third-party assets and embed targets, not a default assumption. ([MDN: IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [MDN: storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Godot 4.7 web-export docs](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html))

## Candidate routes

| Route | Documented fit | Main uncertainty or cost |
|---|---|---|
| **JS/TS simulation + three.js r186** | Direct browser UI integration; custom fixed-step sim; worker option; WebGL 2 baseline with optional WebGPU renderer/fallback; instancing and ray picking primitives. | Game-specific grid/pathfinding, queueing, coaster construction, persistence and UI remain project code. No evidence yet that JS simulation needs Wasm or that WebGPU changes the bottleneck. |
| **Godot 4.7.2-stable web export** | Integrated scene/editor workflow and browser export; single-threaded export has been the preferred default since 4.3 and is documented as more compatible with web-game hosts. | Godot 4 web export targets WebGL 2 through the Compatibility renderer; Forward+/Mobile and WebGPU are unsupported. Godot 4 C# projects cannot export to web. Thread support needs COOP/COEP, with a documented PWA workaround when server headers cannot be set. The docs warn of Safari WebGL 2 issues and recommend Chromium or Firefox where possible. Fit of Godot’s scene/physics model to a grid-first park sim is unmeasured. ([4.7 docs](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html), [living stable docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html), [4.7.2-stable release](https://github.com/godotengine/godot/releases/tag/4.7.2-stable)) |
| **JS/TS front end + conditional Wasm simulation core** | Preserves browser-native UI/rendering while allowing a Rust/C/C++ core or a measured hotspot to be reused. | Adds a second toolchain, data layout and debugging boundary. Threaded Wasm requires cross-origin isolation. Adopt only after simulation-only comparison demonstrates a meaningful gain or existing code reuse offsets the cost. |

These routes are candidates, not a ranking. Three.js is a lean rendering-layer candidate for a custom simulation; Babylon.js is worth a bounded alternative check if its integrated engine services reduce implementation effort. Neither docs feature lists nor release notes establish application performance.

## Minimal experiments (proposed, not run)

1. **Simulation-only:** implement the same deterministic fixed-step workload in TypeScript and a small Wasm core only if there is a plausible native core. Seed one park state with a connected path graph, junctions/dead ends, ride entrances, guest destinations, walking/rerouting, queue joins/leaves, wait estimates, and attraction dispatch. Replay identical commands and random seeds. Check state/output equivalence, then record tick-time distribution (including p50/p95/max), simulated backlog, and memory. If comparing main-thread and worker execution, keep the model and workload identical; report transfer/snapshot costs separately. Do not predeclare a guest-count capacity.
2. **Simulation plus rendering:** replay that park while drawing a representative 3D park with repeated guest/scenery/track meshes, camera movement, placement preview, tile/object picking, and queue updates. Compare WebGL 2 baseline with WebGPU only on environments where `navigator.gpu` and adapter creation succeed. Record simulation tick time alongside frame pacing, input-to-selection responsiveness, and memory. Hold device, browser build, viewport, scene seed and build settings constant; include one lower-capability target once the support matrix is set. Test actual save/load and the intended hosting/iframe setup, especially if COOP/COEP is enabled.

**Unresolved inputs:** target desktop/mobile browsers and minimum GPU; expected park/guest/path workload; acceptable frame and simulation tick budgets; whether game is embedded or uses third-party scripts/assets; and whether saves need cloud sync or portability. These determine whether worker isolation, threaded Wasm, Godot, or WebGPU are viable priorities.
